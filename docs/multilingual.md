# Три языковые версии

По решению заказчика от 28 октября 2026 года: русский (`ru_RU`), английский (`en_US`) и традиционный китайский (`zh_TW`). Публичные языковые адреса: `/`, `/en/`, `/zh-hant/`. Упрощённый китайский не используется.

## Установка на новом сайте или staging

Используется Polylang 3.9.1 из официального каталога WordPress. Версия, лицензия и SHA-256 закреплены в `language-dependency.json`. Исходники плагина не изменяются и не дублируются в Git; проверенный архив получается командой:

```powershell
./scripts/fetch-language-plugin.ps1
```

Архив появляется в `dist/languages`. Его можно установить через админку нового WordPress. Для отдельного локального стенда с Docker:

```sh
docker compose run --rm -v "$PWD/dist/languages:/opt/languages:ro" cli plugin install /opt/languages/polylang.3.9.1.zip --activate
docker compose run --rm cli eval-file /opt/vniipo/prepare-languages.php
docker compose run --rm cli eval-file /opt/vniipo/prepare-languages.php apply
```

Первый запуск показывает план. Второй добавляет три языка, назначает русский только материалам без языка и создаёт 16 черновиков для восьми основных страниц. Повторный запуск не перезаписывает переводы и не создаёт дубли. Настройки применяются только на `local`, `development` и `staging`. Этот сценарий нельзя запускать на действующем конференционном хостинге ради закрытого показа.

Переводы интерфейса находятся в `content/interface-translations.json`: 96 сообщений для английского и традиционного китайского. Черновики основных страниц — `content/translation-drafts.json`. Это краткие переводные версии для редакторской вычитки, а не полный перевод 99 новостей и всех официальных документов. Они по умолчанию не публикуются. Переключатель показывает только опубликованные связанные переводы; Polylang формирует языковые URL и hreflang.

## Работа редактора

В «Языках» выбрать русский как основной. В списке страниц и материалов использовать «+» соответствующего языка, заполнить перевод и связать его с оригиналом. Публиковать после вычитки ответственным переводчиком. Для новых переводов не копируются `_vniipo_key` и source UID: русская запись остаётся единственным владельцем синхронизации с источником.

Доступны отдельные переводы страниц, новостей, документов, вопросов, анонсов, альбомов и информационных блоков. Русские блоки автоматически не подставляются в иностранный интерфейс. Ссылка на раздел без опубликованного перевода ведёт к русскому оригиналу; посетитель видит общее уведомление об этом.

Записи конференций остаются едиными и русскоязычными, как и регистрация и кабинеты прежнего сервиса. Автоматическая генерация языковых копий конференций и заявок не выполняется. Перевод старого конференционного интерфейса — отдельная задача после инвентаризации рабочего портала.

## Проверка

`language-smoke.php prepare` временно публикует черновики только на локальном стенде. JSON состояния сохранить в `.local/language-test-state.json`. `node scripts/language-http-smoke.mjs` проверяет три главные, lang, hreflang, переключатель, галерею и презентационный шаблон. Затем `language-smoke.php cleanup <state>` обязательно возвращает исходные статусы. Не применять тестовый сценарий на production.
