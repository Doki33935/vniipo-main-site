# Интеграция конференционного портала

Интеграция WordPress Conference Service с основным сайтом — обязательное требование пользователя. Исходники уже присутствуют в проекте; перенос рабочих данных и переключение домена выполняются отдельным этапом после сверки.

## Состояние сейчас

Основная главная принадлежит `vniipo-main`. Список `/conferences/` и карточка конференции используют родительскую тему. Плагин конференций активируется в том же WordPress. На странице «Портал конференций» сохранена ссылка https://orenvniipo.online/. Наличие компонентов не означает, что информация с этого домена скопирована в новую БД.

Сохраняются тип `conference`, `_conference_*`, shortcodes, публичные пути регистрации и редакторские пути. Главная нового сайта показывает только опубликованные события. Записи журнала, пользовательские роли и логика определения текущей конференции принадлежат старому плагину.

## Последовательность переноса

1. Зафиксировать версии работающего WordPress, PHP, темы и плагина. Сравнить работающий портал с Git-коммитом из lock-файла. Не считать локальные дампы актуальным production-источником.
2. Получить резервную копию БД и uploads в закрытое хранилище. Проверить восстановление и записать размеры/контрольные суммы. Рабочие данные не помещать в GitHub.
3. Составить реестр конференций, связанных postmeta, options, пользователей, ролей, таблиц заявок, партнёров, журнала и прикреплённых файлов. Зафиксировать количества записей по конференциям и статусам.
4. Выбрать способ миграции. Предпочтительно клонировать проверенную рабочую БД конференционного WordPress на staging и добавить структуру основного сайта поверх неё. Это сохраняет ID и связи. Если к этому времени основной сайт уже содержит рабочие данные, нужен адресный импорт с явным сопоставлением ID, а не полная замена БД.
5. На staging проверить код обновления схемы плагина. Если миграция удаляет legacy-поля, предварительно согласовать состав сохраняемых данных и восстановление.
6. Заменить доменные URL через `wp search-replace --dry-run` с поддержкой сериализованных значений. Исключить GUID; отдельно проверить внешние ссылки, uploads, ссылки программ и карт. Выполнить реальную замену только после проверки отчёта.
7. Добавить/включить `vniipo-core` и дочернюю тему. Выполнить `wp vniipo scaffold` без смены главной, проверить конфликты URL. Назначить новую главную только во время согласованного переключения.
8. Проверить текущую, будущие, черновые и завершённые конференции, несколько площадок и тем/секций, дедлайны, формы, партнёрство, выгрузки и доступ ролей. Проверить прямые старые ссылки на материалы и кабинет.
9. Сравнить контрольные количества заявок и журналов до/после, связность conference_id, пользователей и выбранных секций, наличие файлов и отсутствие дубликатов.
10. Провести пробную миграцию с измерением времени. Определить окно заморозки регистрации и редакторских изменений, ответственного за финальную сверку и точку отката.
11. Во время переноса остановить запись на старом портале или согласовать механизм дельта-переноса. Сделать финальную копию, повторить миграцию, сверить результаты, переключить адреса.
12. Настроить 301 только по подтверждённой таблице прежних и новых URL; исключить кабинеты, административные и POST-эндпоинты из автоматических массовых перенаправлений. Проверить сохранность query-параметров, где они нужны, например conference_id.
13. Наблюдать ошибки, отправку форм, статистику и обращения редакторов. Держать старый контур доступным ответственной команде на время согласованного периода отката.

## Приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Новая главная | Основной сайт, не прежний лендинг одной конференции |
| Архив | Все опубликованные конференции, правильные группы жизненного цикла |
| Карточка | Даты, программа, материалы, темы/секции, площадки и партнёры сохранены |
| Регистрация | Только разрешённая конференция, дедлайн соблюдается, заявка сохраняется однократно |
| Кабинет | Правильные права редактора, автора и ответственного за секции |
| Партнёрство | Новая заявка и существующие заявки доступны уполномоченным ролям |
| Выгрузки | Тестовые данные совпадают с таблицами, доступ ограничен |
| Сверка | Количества и связи сохранены, uploads доступны |
| Откат | Проверена восстановленная копия и последовательность обратного переключения |

Если после переключения в новой БД появились заявки, простой откат на старую БД приведёт к их потере. Перед откатом требуется остановить запись и сохранить/перенести дельту. Переключение DNS само по себе не является полным планом восстановления.
